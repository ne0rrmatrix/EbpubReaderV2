Amazon metadata update — UI concepts

Three placements/flows for offering "update metadata from Amazon" on a per-book basis, matching DisplayBook.App's current color tokens and the Book Details page layout. Open each file directly in a browser — no server needed. Use the demo controls at the bottom of each mockup to step through every state (loading, match found, blocked, not found, applied).

Practicality note: the Python scraper (ScrapeAmazonApi) can't run as-is inside MAUI — there's no Python runtime on iOS/Android. The plan is to port parsing.py's CSS-selector, defensive-fallback approach to C# (AngleSharp + HttpClient), reusing the same fixture-based test strategy (modern/legacy/robot-check/not-found HTML) so it stays testable offline. All three concepts below assume that backend and differ only in where the feature lives and how much of the fetch/match/review flow is exposed.
Book Details · inline panel

V1 — Inline panel

An outline "Update metadata" button under "Open book". Tapping it expands a panel in place with a checklist diff (old vs. new, one checkbox per field) and Apply/Discard. Everything happens on the existing page — no navigation, no modal.

  • Lowest implementation cost, fewest new screens.
  • Diff/checklist keeps the "review before overwrite" safety net.
  • Gets cramped if you also want a manual search / region picker / candidate list.

Book Details · bottom sheet

V2 — Review sheet

A small ↻ icon next to the title opens a bottom sheet holding the whole fetch → review → apply flow, with a compact region + search-text override at the top for when the auto-match is wrong. Book Details itself stays visually unchanged.

  • Keeps Book Details page uncluttered; feature is opt-in and out of the way.
  • Per-field "Keep current / Use Amazon" toggle instead of a plain checkbox — reads a bit clearer.
  • Manual override is present but limited to editing the search query, not raw field values.

Dedicated screen

V3 — Source wizard

A full "Update metadata" screen (reached from Book Details, same pattern as OpdsBookPage): identify (region / ISBN·ASIN / title / author) → candidate picker with match scores → per-field review with editable text overrides → apply. Includes an expandable debug panel with raw fetch status.

  • Closest parity with the Python CLI/plugin's capabilities (search, scoring, manual ASIN entry).
  • Debug panel directly supports the "robust for debugging and testing" requirement.
  • Heaviest to build; best fit if you expect to lean on this a lot or need to unblock bad auto-matches often.

All three share the same underlying states (idle, loading, found/candidates, blocked, not found, applied) — whichever placement you pick, that state machine is the thing to build first and share across views.
